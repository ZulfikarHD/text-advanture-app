# Manual QA — E1.1: Minimal Manual Character CRUD

> **Domain:** `ui` · **Story:** S-1.1.1 / S-1.1.2 (per-story minimal manual character CRUD)
> **Date:** 2026-06-07 (Asia/Jakarta) · **Tester:** _____________ · **Build:** E1.1
> **Rule:** every step uses a visible navigation action (link/button/tab). **No step types a URL to reach a page.** The characters surface is reached by opening a **story card** on the Workspace dashboard, then the **Characters** tab.

## Preconditions

- App running (`composer run dev`) on MariaDB; assets built (`pnpm build` or `pnpm dev`).
- Signed in with an account that owns **at least one story** (create one from the Workspace dashboard if needed).
- No LLM key is required — character authoring is fully manual and makes no model call.

## TC-2 — Create a non-player (NPC) · S-1.1.1

| # | Action (navigation) | Expected |
|---|---------------------|----------|
| 1 | Click **New character** | A dialog opens: Name, the **player** switch (off), Appearance, Base opacity, plus the NPC-only **Folded identity** and **Knowledge boundary** (Knows / Does not know chip inputs) |
| 2 | Enter a Name + Appearance, set Base opacity (0–100) | Fields accept input; base opacity is a number 0–100 |
| 3 | Enter a Folded identity; add ≥1 chip under **Knows** and/or **Does not know** (type, press Enter) | Each entry becomes a removable chip |
| 4 | Click **Create character** | The dialog closes, a success toast shows, and the character appears as a card (name, appearance preview, folded-identity preview, "Knows N / Doesn't know M" badges, an Opacity badge) |

**Pass criteria:** the NPC is created with its appearance, folded identity, and knowledge boundary; no model call happens.
**Result:** ☐ Pass ☐ Fail — Notes: ____________________

## TC-3 — Create the player (appearance only) · S-1.1.2

| # | Action (navigation) | Expected |
|---|---------------------|----------|

**Pass criteria:** a player captures only name + appearance + base opacity (no interiority fields); the card is clearly marked as the player.

## TC-4 — Validation · S-1.1.1 / S-1.1.2

| # | Action (navigation) | Expected |
|---|---------------------|----------|
| 1 | Open **New character**, leave **Name** blank, submit | An error: "Give the character a name." — no save |
| 2 | As an **NPC** (player off), clear **Folded identity**, submit | An error: "Folded identity is required for a non-player character." — no save |
| 3 | As an **NPC**, leave **both** knowledge-boundary lists empty, submit | An error: "Knowledge boundary is required: list at least one thing this character knows or does not know." — no save |
| 4 | With a player already present, open **New character** | The **player** switch is **disabled/locked off** with a note ("This story already has a player character"); creating another player is impossible from the UI |

**Pass criteria:** required-field errors show and nothing saves; the knowledge boundary is mandatory for an NPC; only one player is possible per story.
**Result:** ☐ Pass ☐ Fail — Notes: ____________________

## TC-5 — Edit a character · S-1.1.1

| # | Action (navigation) | Expected |
|---|---------------------|----------|
| 1 | On a character card, click the **edit** (pencil) button | The dialog opens **pre-filled** with that character's name, appearance, opacity, player flag, and (for an NPC) folded identity + knowledge boundary |
| 2 | Change a field, toggle a chip, click **Save changes** | The dialog closes, a success toast shows, and the card reflects the edits |
| 3 | Edit the **player** character | The player switch stays editable (editing the existing player is allowed); switching it off reveals the NPC fields |

**Pass criteria:** edit pre-fills correctly and persists; no draft leaks from a previous create/edit; the existing player is editable.

## TC-8 — Ownership isolation (automated-backed)

Cross-story / cross-owner access (404) would require typing another scope's URL, which this checklist forbids, so it is locked by automated tests instead:

**Manual evidence:** while signed in, no visible navigation exposes another story's characters.

## UX / Law-of-UX observations

- **Single primary action** (Hick's): one **New character** per view. ✔
- **Confirm destructive actions:** delete uses `useConfirm`, not `window.confirm`. ✔
- **Four states:** empty (teaching), success (toast), error (inline validation); the list is the success state. ✔
- **Progressive disclosure:** the player switch hides the NPC-only fields a player never needs. ✔
- **Touch targets:** dialog buttons and card actions meet ≥44px (`h-11` / `size-9` icon affordances). ✔
- **Tokens + dark parity:** all surfaces use semantic tokens (no hardcoded colors). ✔

## UX Critical Violation check

> **None found.** The characters surface is reached through visible navigation (story card → Characters tab). Create/edit happen in a dialog; deletes are confirmed. The cross-scope 404 isolation, which would require typing another scope's URL to demo, is validated by automated tests.
